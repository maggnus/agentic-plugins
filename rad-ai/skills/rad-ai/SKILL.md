# RAD AI

Optimize time to accepted outcomes; quality constraints are fixed. The method is experimental. Respect scope, project rules and existing authorization. Roles name duties, not agents: any runtime, provider or model may fill a role, and project rules choose which; nothing here depends on one.

An outcome is complete only after a separate review accepts its current revision at 10, or at 9 with exceptions citing an owner decision. A known in-scope defect, a missing required check, a reviewer's proposal to defer or `UNVERIFIED` never completes an outcome; correct defects and resubmit, and report `UNVERIFIED` to the owner as a blocking condition.

## Cycle

1. **Frame.** Inspect requirements, architecture and revision. Record the user outcome, exclusions, observable acceptance and required checks, the invariants that need discriminating evidence, the required observations (real dependencies, environments, user paths), dependencies, budget and current plan in existing records; never narrow acceptance to fit an implementation. Clarify uncertainty affecting the next decision. Planning requests end with a plan.
2. **Experiment.** Test consequential uncertainty before dependent work. Product assumptions require representative feedback; technical assumptions require discriminating evidence. Agent agreement is insufficient. Record observations and decisions. Discard prototypes, retain experiments, or apply production acceptance. Established corrections need no prototype.
3. **Partition.** Define assessable outcomes using [contracts](references/contracts.md), one record per outcome that will be accepted separately; investigate broad dependencies using [scale](references/scale.md). Start with one implementer. Delegate authorized independent outcomes within review capacity. Serialize shared-workspace writes; concurrent writers require verified isolation. Shared contracts precede consumers. Reduce concurrency as queues, conflicts or rework grow.
4. **Implement.** Preserve boundaries, inspect consumers and make minimal complete changes. Justify new dependencies against alternatives. Test behavior and failure paths, including a discriminating failing form for significant changes. Use the included [implementation role](../rad-ai-build/SKILL.md) when delegating; otherwise perform these duties directly.
5. **Accept.** Local reversible consequences require targeted checks and complete diff assessment; cross-module or user-visible changes add consumer checks. Critical consequences, including data loss, access, disclosure or irreversible effects, require discriminating evidence. Only a separate review context accepts, using the included [review role](../rad-ai-review/SKILL.md): a subagent, another session or agent, or the owner. Implementers and coordinators submit. Give every review the owner's words or source records, the contract and all prior findings, without scores; pass the implementer's statements as claims with their evidence, never as conclusions. Only the contract, not the reviewer or the implementer, marks an observation as not required, and every observation it postpones is recorded with the outcome that will make it. Missing required evidence returns; report `UNVERIFIED` only when no separate review or required observation can be obtained, and do not deliver. Acceptance binds to requirements and revision. Correct every in-scope defect and resubmit; a prior defect closes only when resolved on the current revision or excepted by the owner. Only the owner defers a defect. When a corrected resubmission is returned for a second defect of one class in the same component, stop patching instances: return the component to design and close the class with one general rule and a coverage table. The outcome keeps its identity and round history through redesign; the redesigned candidate advances the round once. Defects of one class listed together in one review are one defect. Rounds after the first assess the delta, the prior findings and whatever the delta affects; unchanged code is not exempt from new defects, but rerun only evidence the delta can change.
6. **Integrate.** Combine accepted outcomes by dependency. A candidate that contained the current base when its last review accepted it is the combined revision; otherwise a separate review accepts the combined revision's consumers and user paths. Make the postponed observations no later than the outcome they were recorded with; a stage with one outstanding is not complete. Invalidate affected evidence after requirements or revision changes. Without new evidence, split, revise the approach or identify the blocking condition.
7. **Deliver and learn.** Perform authorized delivery with observed success and recovery. Verify the target and obtain feedback; identify local acceptance when delivery is outside scope. Budget limits reduce scope without weakening quality; removing an in-scope requirement or defect requires an owner decision. Choose subsequent work from observations. A defect class returned in one outcome becomes a contract line of the stage's later outcomes, so it is prevented, not found again.

## Reports

Text reviews start `ACCEPT Rn (s/10)` or `RETURN Rn (s/10)`; unavailable assessment uses `UNVERIFIED Rn (n/a)`. Rounds start at 1 per outcome and advance after corrected resubmission; repeats, restarts and reviewer changes preserve them. Score the lowest applicable code/evidence/user-path axis using the contract rubric. Acceptance requires 10, or 9 with exceptions citing an owner decision; lower scores return.

Before every progress report, reconcile current task and decision records; calculate `<index> (p%) ✅ D 📋 N ⚙️ A 🙋 B`, followed by ` ⛔ K` only when K tasks are blocked. The line carries the stage's index alone (`W5`), never a word naming or describing the stage, and no other text. Exclude cancelled tasks. N counts eligible tasks; D counts currently completed outcomes; A counts implementation/review; B counts distinct unresolved human-only decisions. Round p=100D/N half-up; empty stages use 0%. Never reuse displayed values or invent missing records. The optional [formatter](scripts/report.py) implements these rules.

Preserve completed independent work after interruption. Report revision, observed commands, exit statuses, limitations and next step. Measure elapsed time, effort, cost, waiting and rework; compare improvement against a baseline. Record per outcome, in its record at each verdict, the review rounds, elapsed hours and tokens used when observable, never estimated, so repeated rounds on one class of defect are visible. When an outcome exceeds its budget or its rounds stop converging (two consecutive returns with no load-bearing defect), stop and reframe: split it, narrow the contract's required evidence with the owner, or record the blocking decision.
