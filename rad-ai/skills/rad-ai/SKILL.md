# RAD AI

Optimize time to accepted outcomes; quality constraints are fixed. The method is experimental. Respect scope, project rules and existing authorization. Roles name duties, not agents: any runtime, provider or model may fill a role, and project rules choose which; nothing here depends on one.

## Completion

The method regulates itself: the roles decide and never wait for the owner, who decides only changes to the owner's own requirements, critical consequences left without evidence, and irreversible actions.

- An outcome is complete when a separate review has accepted it and every correction from any of its reviews is closed. Acceptance carries to a final revision that differs only by correction fixes whose checks passed.
- Findings have three kinds, defined in [contracts](references/contracts.md). Only a **blocking defect**, a violation of what the owner, the contract or project rules require of the delivered result, returns an outcome for another round. A **correction**, any other flaw whose fix a check confirms, is fixed and closed by the coordinator when that check passes, with no further review. A **note** becomes a task where it belongs or is declined with a reason; it never blocks and is not investigated here.
- An **experiment** answers one question from a closed list of observations. One review accepts it when the answer, "no" included, and the constraints later outcomes rely on are reproduced; its prototype code and the wording of its record are not assessed.
- What a reviewer observed is evidence: add it to the record, and never run a round for the implementer to reproduce it.
- The contract sets a time budget for the whole outcome and a round limit (two unless risk sets another). At the budget the implementer submits what exists. When either is spent with a blocking defect open, change the approach or split the outcome: the original is cancelled, naming its successors, each a new outcome. Record it blocked only when neither exists, naming what unblocks it.
- A contract is fixed when implementation starts; what is found later becomes a new outcome. Only a gap that leaves an owner requirement unverified amends it, once.

## Cycle

1. **Frame.** Inspect requirements, architecture and revision. Record the user outcome, exclusions, observable acceptance and required checks, the invariants that need discriminating evidence, the required observations (real dependencies, environments, user paths), dependencies, time budget, round limit and current plan in existing records; never narrow acceptance to fit an implementation. Clarify uncertainty affecting the next decision. Planning requests end with a plan.
2. **Experiment.** Test consequential uncertainty before dependent work, one question and a closed list of observations per experiment. Product assumptions require representative feedback; technical assumptions require discriminating evidence. Agent agreement is insufficient. Record observations and decisions. Discard prototypes, retain experiments, or apply production acceptance. Established corrections need no prototype.
3. **Partition.** Define assessable outcomes using [contracts](references/contracts.md), one record per outcome that will be accepted separately; investigate broad dependencies using [scale](references/scale.md). Start with one implementer. Delegate authorized independent outcomes within review capacity. Serialize shared-workspace writes; concurrent writers require verified isolation. Shared contracts precede consumers. Reduce concurrency as queues, conflicts or rework grow.
4. **Implement.** Preserve boundaries, inspect consumers and make minimal complete changes. Justify new dependencies against alternatives. Test behavior and failure paths, including a discriminating failing form for significant changes. Use the included [implementation role](../rad-ai-build/SKILL.md) when delegating; otherwise perform these duties directly.
5. **Accept.** Local reversible consequences require targeted checks and complete diff assessment; cross-module or user-visible changes add consumer checks. Critical consequences, including data loss, access, disclosure or irreversible effects, require discriminating evidence. Only a separate review context accepts, using the included [review role](../rad-ai-review/SKILL.md): a subagent, another session or agent, or the owner. Implementers and coordinators submit. Give every review the owner's words or source records, the contract and all prior findings; pass the implementer's statements as claims with their evidence, never as conclusions. Only the contract, not the reviewer or the implementer, marks an observation as not required, and every observation it postpones is recorded with the outcome that will make it. Report `UNVERIFIED` only when no separate review or required observation can be obtained; the outcome is then blocked, recorded with what would unblock it. Acceptance binds to requirements and revision.
6. **Integrate.** Combine accepted outcomes by dependency. A candidate that contained the current base when its last review accepted it is the combined revision; otherwise a separate review accepts the combined revision's consumers and user paths. Make the postponed observations no later than the outcome they were recorded with; a stage with one outstanding is not complete. Invalidate affected evidence after requirements or revision changes.
7. **Deliver and learn.** Perform authorized delivery with observed success and recovery. Verify the target and obtain feedback; identify local acceptance when delivery is outside scope. Budget limits reduce scope without weakening quality. Choose subsequent work from observations. A class of blocking defect returned in one outcome becomes a contract line of the stage's later outcomes, so it is prevented, not found again.

## Reports

Text reviews start `ACCEPT Rn (blocking 0, corrections c)` or `RETURN Rn (blocking b, corrections c)`, counting open findings; unavailable assessment uses `UNVERIFIED Rn`. An accepted outcome with corrections open stays in review until each check has passed; the formatter's `verdict` command checks the review record and `complete` the closure, where each closed correction carries `result` and `revision` and the record carries `final` when fixes followed the accepted commit. Rounds start at 1 per outcome and advance after corrected resubmission; repeats, restarts and reviewer changes preserve them.

Before every progress report, reconcile current task and decision records; calculate `<index> (p%) ✅ D 📋 W ⚙️ A 🙋 B`, with ` ⛔ K` before `🙋` only when K tasks are blocked; the owner's decisions `🙋 B` are always last. The task counts add up to the stage: D + W + A + K = N, and p is D of N. The line carries the stage's index alone (`W5`), never a word naming or describing the stage, and no other text. Exclude cancelled tasks. N counts eligible tasks; D counts currently completed outcomes; W counts tasks waiting to start; A counts implementation/review; K counts blocked tasks; B counts distinct unresolved human-only decisions. Round p=100D/N half-up; empty stages use 0%. Never reuse displayed values or invent missing records. The optional [formatter](scripts/report.py) implements these rules.

Preserve completed independent work after interruption. Report revision, observed commands, exit statuses, limitations and next step. Measure elapsed time, effort, cost, waiting and rework; compare improvement against a baseline. Record per outcome, in its record at each verdict, the review rounds, elapsed hours and tokens used when observable, never estimated, so repeated rounds on one class of defect are visible.
