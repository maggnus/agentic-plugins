# План создания `rad-ai`

## Состояние и цель

Подготовлен первый этап — план. Дата составления: 3 октября 2026 года.
Выполнены обзор соседних плагинов и предварительный поиск источников. Полное исследование,
адаптация методологии, мысленные эксперименты, практическая проверка и первый выпуск
навыков остаются впереди. Предлагаемые ниже правила и состав навыков — гипотезы проекта.

**Результат:** плагин для Codex и Claude Code, который проводит разработку приложения
через короткие циклы уточнения потребности, проверки решения, реализации и ввода в
эксплуатацию. Скорость измеряется временем до принятого результата и пропускной
способностью при соблюдении требований качества. Объём созданного кода и число
одновременно работающих агентов не являются показателями успеха.

Метод предназначен для новых приложений и изменений существующих систем, от небольшого
репозитория до кодовой базы, которую невозможно целиком поместить в контекст агента.
Первый выпуск должен явно перечислять проверенные условия применения и ограничения.
Универсальное ускорение и пригодность для гигантских систем нельзя обещать по результатам
работы на небольшом примере.

## Границы относительно соседних плагинов

| Плагин | Существующая ответственность | Граница `rad-ai` |
| --- | --- | --- |
| `brief` | Постановка продукта, ограничения, проверяемые результаты и порядок первых частей | Принимать имеющуюся постановку; при её отсутствии проводить только необходимое уточнение текущего цикла |
| `team` | Выполнение и проверка изменений небольшой командой в общей рабочей копии | Определять цикл RAD, способ разделения работы и условия переходов; учитывать ограничения общей копии |
| `paseo-cto` | Управление изолированными агентами Paseo и включение принятых изменений | Использовать подходящий способ исполнения без обязательной зависимости от Paseo |
| `rad-ai` | Планируемая ответственность | Управлять проверкой гипотез, обратной связью, ограничением объёма цикла и качеством результата на разных масштабах |

Самостоятельный запуск должен быть возможен на каждой платформе. Совместное использование
с соседними плагинами не должно создавать двух руководителей, конкурирующих записей
состояния или противоречивых критериев приёмки. Совместимость требует отдельной проверки.
Не включать в первый выпуск собственную среду исполнения агентов, систему поиска по всему
репозиторию или универсальную базу задач без доказанной необходимости.

## Этап 2: программа исследования

Изучить RAD по первоисточнику James Martin, включая планирование требований, совместное
проектирование с пользователями, построение и переход к эксплуатации. Отдельно выяснить
роль прототипов, повторного использования, инструментальной поддержки, ограниченных
по времени циклов и постоянной обратной связи. Проверить исходные ограничения метода:
размер и связность системы, доступность пользователей, нефункциональные требования,
интеграции и пригодность прототипа для дальнейшего развития.

Сопоставить RAD со следующими подходами, отбирая положения по пользе для цели:

- DSDM: приоритеты, ограничение времени и объёма, условия сохранения качества.
- Спиральная модель: порядок работ по неопределённости и риску.
- Итерационная и инкрементная разработка: различие проверки гипотезы и поставки функции.
- Модульное проектирование: сокрытие решений, интерфейсы и независимость изменений.
- Непрерывная интеграция и поставка: раннее обнаружение несовместимости, малые изменения,
  эксплуатационная проверка и восстановление после неудачного выпуска.
- Исследования производительности разработчиков и агентов: что именно измеряется,
  насколько достоверен результат и можно ли перенести его на нашу задачу.

Разделять историческую методологию, теоретическое обоснование, эмпирическое свидетельство
и собственное проектное решение. Популярность приёма не доказывает его эффективность.
Обзорные статьи использовать для поиска первоисточников; выводы основывать на самих
работах, данных и официальных описаниях методов.

Для каждого источника сохранять автора, год, версию или дату обращения, метод исследования,
выборку, условия, результат и ограничения. Для каждого вывода — цепочку
«источник → интерпретация → правило `rad-ai` → проверка, способная его опровергнуть».
Если доступно только описание или аннотация, отмечать это и не делать выводов о полном тексте.
Численные результаты старых моделей не переносить на текущие инструменты без проверки.

## Этап 3: специфика разработки агентами

Построить модель отказов и возможностей по семи направлениям:

1. **Контекст.** Как найти достаточную область кода, проверить происхождение сведений,
   распознать неполноту и обновить контекст после изменения базового коммита.
2. **Декомпозиция.** Как отделить независимые результаты от связанных правок;
   учитывать общие интерфейсы, схемы данных, сборку и порядок зависимостей.
3. **Координация.** Как передавать цель, ограничения, исходный коммит, область записи,
   критерии приёмки и свидетельства; когда выгоднее один агент.
4. **Изоляция.** Различать общую рабочую копию и отдельные рабочие деревья Git.
   В общей копии записи выполнять последовательно; изоляция файлов не снимает
   конфликтов интерфейсов и эксплуатационных ресурсов.
5. **Надёжность.** Рассмотреть вымышленные утверждения, ложные успешные отчёты,
   общие ошибки автора и проверяющего, подгонку под тест и инструкции в недоверенных данных.
6. **Состояние.** После прерывания восстанавливать работу по Git, действующей документации
   и проверяемым результатам; отвергать устаревшие отчёты и изменения не от согласованной базы.
7. **Платформы.** Проверить актуальные возможности и ограничения Codex и Claude Code
   по официальной документации и реальным запускам. Записать версии платформ, инструменты
   и различия; не считать одинаковое имя навыка доказательством одинакового поведения.

Модели, уровень рассуждения и бюджеты записывать в протокол запуска. Метод не должен
зависеть от неназванной модели, неограниченного числа агентов или неучтённого труда человека.
Полномочия агентов выводить из задачи и правил проекта; методология не расширяет их сама.

## Этап 4: предполагаемый цикл RAD для ИИ

Это исходная конструкция для исследования и проверки, не окончательная инструкция навыка.

| Фаза RAD | Действия в агентной среде | Результат и условие перехода |
| --- | --- | --- |
| Планирование требований | Уточнить пользовательский результат, границы, неопределённости, риск и бюджет цикла; изучить затронутую архитектуру | Проверяемый сценарий, неизменяемые требования качества и ограниченный объём работ |
| Совместное проектирование | Получить обратную связь владельца или пользователей; проверить наиболее опасное предположение прототипом либо архитектурным экспериментом | Наблюдение, подтверждающее или отвергающее гипотезу; принятое решение и судьба прототипа |
| Построение | Разделить результат на части, каждая из которых проводит сценарий через необходимые слои; согласовать контракты; реализовать и рано объединять изменения | Работающий результат на согласованной базе, проверки затронутых потребителей и независимая оценка по риску |
| Переход к эксплуатации | Пройти пользовательский сценарий, проверить совместимость, выпуск, наблюдаемость и восстановление; выполнить разрешённую поставку | Подтверждённый результат в целевой среде, обратная связь и решение о следующем цикле |

Возвраты между фазами допустимы по наблюдаемым причинам: неверная потребность,
опровергнутая гипотеза, несовместимый контракт или провал приёмки. Не вводить обязательный
прототип для уже понятного локального исправления. При изменении предпосылки пересматривать
зависимые работы, а не продолжать их по старому заданию.

Предварительные правила, которые должны выдержать эксперименты:

- Срок цикла, стоимость и незавершённая работа ограничены; при исчерпании бюджета
  уменьшается объём или меняется решение. Требования качества не смягчаются ради завершения.
- Пользовательская обратная связь и техническая приёмка имеют разные основания.
  Агент может подготовить сценарий, но не выдаёт своё одобрение за мнение пользователя.
- Прототип получает явное решение: удалить, оставить как эксперимент или превратить
  в эксплуатационный код после требуемых проверок. Его происхождение не отменяет приёмку.
- Архитектурное решение фиксирует альтернативы, ограничения и условие пересмотра.
  Ввод новой общей абстракции требует наблюдаемой потребности; нарушение границ не оправдывается скоростью.
- Число исполнителей ограничивается независимыми областями изменений и способностью
  проверять и объединять результат. При росте очереди проверки или конфликтов параллельность уменьшается.
- Приёмка связана с точным коммитом и требованиями. Изменение базы требует проверки
  актуальности свидетельств; отчёт агента сам по себе не является доказательством.

## Масштабирование без чтения всего репозитория

Измерять масштаб по размеру собственного кода, числу модулей и потребителей, связности,
времени проверок и доступному контексту. Зафиксировать критерии групп до испытаний;
зависимости и сгенерированный код считать отдельно.

| Условия проекта | Предполагаемый способ работы | Что проверить |
| --- | --- | --- |
| Небольшое приложение, одна предметная область | Краткий план, минимальный набор документов, один исполнитель; дополнительная проверка по риску | Не съедают ли организация и документация выигрыш от метода |
| Большая существующая система с несколькими модулями | Карта области изменения и потребителей, локальные контракты, ограниченное число изолированных работ | Не пропущены ли косвенные потребители и проверки объединённого результата |
| Гигантская база, множество областей, полное чтение невозможно | Постепенное изучение от точки входа и графа зависимостей; координация по модулям, последовательные изменения общих контрактов | Достаточен ли ограниченный контекст; сохраняются ли совместимость и общая архитектура без полного обзора |

Первый цикл сначала находит действующие архитектурные ограничения и повторно использует
существующие документы и проверки. Новые записи появляются только для недостающих решений.
Проверки выбирать по области воздействия; расширять их для общих библиотек, схем,
инфраструктуры и неизвестных зависимостей. Дефекты за границами задачи фиксировать отдельно.

Для гигантской базы предусмотреть действительный проект соответствующего масштаба и
изменение с внешними потребителями. Искусственное увеличение числа файлов не проверяет
понимание связности. Если такого испытания нет, в выпуске масштаб объявляется непроверенным.

## Этап 5: мысленные эксперименты

Для каждого сценария пройти весь цикл вручную: вход → неопределённость → роли и
контекст → решение → реализация → интеграция → приёмка → обратная связь.
Записать ошибочный ход, момент его обнаружения, восстановление и стоимость предотвращения.

| Сценарий | Вопрос, на который метод обязан дать ответ |
| --- | --- |
| Небольшое новое приложение с неясной потребностью | Как получить первый полезный сценарий и обратную связь без лишних ролей и документов |
| Локальное исправление в большом монолитном приложении | Как найти нужный контекст и не превратить исправление в перепроектирование |
| Изменение общей библиотеки с несколькими потребителями | Кто согласует контракт и как проверить совместимость объединённого результата |
| Изменение формата данных и длительный переход между версиями | Как удержать инварианты и спланировать восстановление, если обычный откат невозможен |
| Три исполнителя меняют соседние модули | Как обнаружить смысловой конфликт при отсутствии конфликта строк |
| Изменилась потребность после прототипа | Что отменить, какие свидетельства устарели и что можно использовать повторно |
| Автор и проверяющий допускают одну ошибку | Какая независимая проверка способна обнаружить её |
| Исчерпан бюджет, потерян контекст или прерван агент | Как восстановить достоверное состояние и выбрать следующий шаг |
| Проверки успешны, пользовательская задача не решена | Почему техническое прохождение не означает приёмку |
| Гигантская база с неизвестным косвенным потребителем | Как обнаружить неполноту анализа до принятия изменения |

Мысленные эксперименты выявляют противоречия. Они не доказывают ускорение, качество
получаемого кода или работоспособность на платформе; это предмет практической проверки.

## Этап 6: практическая проверка и измерение эффекта

До запусков определить задачи, исходные коммиты, критерии приёмки, лимиты времени и
стоимости, рубрику архитектурной оценки и минимальный полезный выигрыш. Порог выигрыша
выбирать после короткой оценки разброса на отдельных подготовительных задачах и фиксировать
до сравнительных запусков. Не менять его после получения результатов.

Сравнить три режима: обычная работа одного агента; цикл `rad-ai` с одним агентом;
цикл `rad-ai` с несколькими агентами там, где работа допускает разделение. Это отделяет
эффект методологии от эффекта параллельности. При необходимости отдельно сравнить
с `team` или `paseo-cto`, сохранив одинаковые критерии и не смешивая способы исполнения.

Начать с подготовительных запусков на небольшом и крупном проекте. Затем использовать
задачи из разных сценариев предыдущего этапа, включая изменение общего контракта,
неуспешный путь, восстановление после прерывания и работу в гигантской базе. Указать
проект, измеренный масштаб, лицензию и доступность воспроизведения. Новые задачи выбирать
так, чтобы эталонное решение не попало в контекст исполнителя.

Добавить последовательность из нескольких циклов в одной системе: первая функция,
изменение потребности, расширение и изменение общего контракта. Проверить, как меняются
стоимость следующих изменений, связность, дублирование и накопленные ограничения.
Приёмка единичного изменения не подтверждает сохранение архитектуры при длительной
интенсивной разработке. Сопоставлять итоговое состояние систем с одинаковым результатом.

Фиксировать модель и её настройки, версию платформы, инструменты, предел параллельности,
бюджет и вмешательства человека. Каждый режим начинает с той же исходной версии;
переписка и результаты соседнего запуска ему недоступны. Менять порядок режимов,
повторять запуски и заранее определить обработку сбоев. Неудачи, превышения бюджета и
незавершённые работы включаются в результат, а не исключаются из сравнения.
Объём повторов и стоимость всего испытания определить в протоколе до выполнения.

| Ось оценки | Измерение |
| --- | --- |
| Пользовательский результат | Прохождение согласованного сценария через реальную поверхность приложения |
| Качество кода | Корректность, необходимые отрицательные проверки, соответствие проекту, читаемость и отсутствие случайных изменений |
| Архитектура | Соблюдение границ и инвариантов, совместимость потребителей, оправданность зависимостей и абстракций |
| Скорость | Полное время от начала задачи до приёмки с учётом изучения, координации, ожидания, исправлений и проверок |
| Пропускная способность | Число принятых результатов за фиксированный период при одинаковых требованиях |
| Затраты | Расход модели, вычислений и время человека; отдельно задержка и суммарный труд всех агентов |
| Переделки и устойчивость | Возвраты, конфликты, дефекты после приёмки и время восстановления |
| Накладные расходы | Время на документы, передачу контекста, очередь проверки и объединение изменений |

Приёмку проводить по заданию, исходному коду и наблюдаемому поведению, независимо от
самооценки исполнителя. Где возможно, проверяющему не сообщать режим запуска. Для
принципиальных требований показать, что проверка отвергает намеренно нарушенный инвариант.
Результаты сохранять с командами, кодами завершения и точными коммитами.

Качество является условием допуска, а не величиной, которую можно компенсировать скоростью.
Открытое существенное нарушение сценария, инварианта или архитектурного контракта
исключает принятие. При соблюдении требований отдельно сравнить время и стоимость.
Привести разброс и неопределённость; небольшой пробный набор подтверждает выполнимость,
но не доказывает универсальное превосходство.

Если выигрыш не обнаружен, изменить конкретное правило, повторить относящиеся к нему
испытания или сузить область применения. Не добавлять агентов только ради улучшения
показателя числа параллельных работ. Выпускать как экспериментальный метод, если
выполнимость показана, а эффект ещё не подтверждён; обозначить это в документации.

## Этап 7: первый набор навыков

Начальная гипотеза — один основной навык `rad-ai`, проводящий весь цикл, и отдельные
ролевые навыки лишь для обязанностей, которые требуют независимого контекста или повторного
использования. Возможные роли: исследование неопределённости, реализация, независимая
приёмка. Число ролей и окончательные имена определить по результатам этапов 4–6.
Фаза методологии сама по себе не требует отдельного навыка.

В основной инструкции оставить принятие решений и краткий порядок работы. Подробные
основания и примеры загружать по необходимости из материалов навыка. Скрипты вводить
только для операций, которым нужна воспроизводимость; не дублировать инструменты проекта.
Каждый навык получает точный повод запуска, вход, результат, ограничения и правило
действий при неполном контексте. Состояние проекта хранится в существующей системе;
минимальный новый формат нужен только при её отсутствии.

Обязательная упаковка по образцу соседних плагинов:

- `rad-ai/.claude-plugin/plugin.json` и `rad-ai/.codex-plugin/plugin.json`;
- общий каталог `rad-ai/skills/`, `SKILL.md` для каждого навыка и `agents/openai.yaml`
  для Codex;
- одна запись `rad-ai` в корневом каталоге `.claude-plugin/marketplace.json`;
- README с назначением, ограничениями, проверенными сценариями, вызовом на обеих
  платформах и установкой только из GitHub по опубликованному тегу;
- содержательные проверки контрактов и включение нового плагина в проверки общего выпуска.

Учесть, что `.github/scripts/test-release.mjs` и
`paseo-cto/scripts/check-distribution-sync.sh` сейчас явно перечисляют четыре плагина.
Добавить `rad-ai` в охват при упаковке и проверить общий технический суффикс Codex,
синхронность манифестов, описаний и тегов в README. Выбрать минимальное изменение
проверок, которое не оставит новый плагин вне испытания выпуска.

Проверка навыков должна проверять поведение: нарушение контракта, отсутствие обратной
связи, устаревшая база, конфликт записей и ложный успешный отчёт должны менять решение.
Поиск нужной строки в инструкции проверяет упаковку, но не доказательство методологии.

## Этап 8: публикация и критерии приёмки

Применять [AGENTS.md](../AGENTS.md) и [порядок выпуска](../README.md#release).
Не устанавливать плагин из рабочей копии, не копировать его в каталоги установки
и не изменять кэш вручную. Анализ файлов, проверка упаковки и испытательные файлы
временного Git-репозитория не являются установкой.

При добавлении манифестов использовать текущую общую версию и существующий общий
суффикс Codex как исходное состояние. Следующую версию, технический суффикс, коммит
выпуска и тег создаёт только semantic-release в GitHub Actions после отправки в `main`.
Версии вручную не повышать, опубликованные теги не перемещать.

Последовательность: проверить изменения и выполнить `npm ci` и `npm test`; отправить
исходные изменения в `main`; дождаться успешного GitHub Actions; проверить GitHub Release,
тег, коммит и версии всех манифестов; установить опубликованный `rad-ai` только из
`maggnus/agentic-plugins` с этим неизменяемым тегом; выполнить согласованный проверочный
сценарий на Codex и Claude Code. Необходимые исправления выпускаются следующим тегом.

Первый выпуск навыков принят, когда:

- [ ] Исследование отделяет источники, выводы и проектные гипотезы; пределы доказательств обозначены.
- [ ] Полный цикл проходит от пользовательской потребности до принятого результата и обратной связи.
- [ ] Качество кода, архитектурные инварианты и совместимость проверяются независимо от скорости.
- [ ] Показаны случаи полезной параллельности и случаи выбора одного исполнителя.
- [ ] Практически проверены небольшой и крупный проекты, прерывание работы и изменение общего контракта.
- [ ] Гигантская база проверена на реальном проекте либо явно указана как непроверенный масштаб без заявления о подтверждённой пригодности.
- [ ] Для каждого заявленного улучшения есть сравнительное измерение; неподтверждённый эффект отмечен как экспериментальный.
- [ ] Общие навыки упакованы для обеих платформ, а новый плагин охвачен проверками выпуска.
- [ ] GitHub Actions опубликовал единый выпуск; тег, GitHub Release и версии проверены.
- [ ] Установка из опубликованного тега и запуск навыков проверены на Codex и Claude Code.

Если одна из платформ недоступна для проверки, фиксировать точный пропуск и следующий шаг;
проверку обеих платформ не объявлять завершённой по чтению манифестов.

## Ближайший шаг

Начать этап 2: изучить первоисточники, составить матрицу доказательств и ограничений,
затем перейти к модели разработки агентами. Перед практическими запусками определить
проекты для малой, крупной и гигантской базы, модели и бюджет испытаний. Эти решения
нужны для измерений; они не препятствуют исследованию основ и проектированию метода.
