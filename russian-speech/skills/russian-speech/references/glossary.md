# Русский технический стиль для инженерного агента

## Назначение

Этот файл задаёт нормативный русский язык для инженерных ответов, статусов, ревью, ADR, описаний CI/CD, Kubernetes, GCP, GitOps, IAM и тестирования.

Главное правило: **переводить смысл, а не английские слова по отдельности**.

Текст должен звучать как русскоязычная техническая документация, написанная инженером: точно, связно, без машинных калек, без лишней разговорности и без искусственного «обрусения» общепринятых терминов.

---

## 1. Обязательные правила

1. Не переводить английские инженерные метафоры буквально, если в русском языке нет такого термина.
2. Сначала определить технический смысл слова в данном контексте, затем выбирать русский эквивалент.
3. Имена ресурсов, API, файлов, классов, полей, команд, Kubernetes kinds, environment IDs и project-specific identifiers не переводить:
   - `Cloud Build`
   - `Cloud Run`
   - `Flux`
   - `Kustomization`
   - `ConfigMap`
   - `Secret`
   - `prod-preview`
   - `fast-promote`
   - `release.yaml`
4. Английский термин допустим, если он является общепринятым профессиональным термином или точным именем сущности. Русское предложение вокруг него всё равно должно быть грамматически естественным.
5. Не создавать русские слова механическим переводом:
   - `lane` ≠ «полоса»
   - `identity` ≠ «личность»
   - `reconcile` ≠ «примирять»
   - `gate` ≠ «шлюз»
   - `trigger` ≠ «толчок»
   - `frontier` ≠ «фронт»
   - `sweep` ≠ «развёртка»
6. Не использовать неодушевлённые технические сущности как людей без необходимости:
   - плохо: «правило узнаёт», «шлюз умеет упасть», «карточка ждёт среду»;
   - хорошо: «правило определяет», «проверка должна завершаться ошибкой», «задачу можно продолжить после появления среды».
7. Не описывать состояние CI/CD цветами, если речь не о буквальном UI:
   - «проверка покраснела» → «проверка завершилась ошибкой»;
   - «шлюз стал зелёным» → «проверка успешно проходит».
8. Не заменять точные инженерные действия метафорами:
   - «стучится не в ту дверь» → «обращается к неверному endpoint/порту»;
   - «доходит до среды» → «автоматически развёртывается в среде».
9. Не использовать канцелярские или псевдонаучные конструкции там, где есть простой технический глагол.
10. В одном абзаце использовать один устойчивый термин для одной сущности. Не чередовать «полоса / контур / ветвь» без причины.

### Нормативные примеры

Плохо:

> Полоса публикует событие и следующая полоса стартует.

Хорошо:

> После успешного завершения контур публикует событие в Pub/Sub; это событие запускает следующий этап пайплайна.

Плохо:

> Релизная сборка планирует и подаёт сборку девяти образов.

Хорошо:

> Релизный этап формирует конфигурацию дочерней сборки и отправляет на выполнение сборку девяти контейнерных образов.

Плохо:

> Глубокая полоса доказывает совместимость миграций.

Хорошо:

> Расширенный контур проверяет совместимость миграций и подтверждает результат перед продвижением версии.

### Особое правило для `identity`

Не переводить `identity` одинаково во всех случаях.

Выбирать по реальной сущности:

- Google service account → **сервисная учётная запись**;
- IAM principal → **субъект IAM** или **principal**;
- workload identity mechanism → **Workload Identity**;
- actor that performs a build → **учётная запись, от имени которой выполняется сборка**;
- identifier of a source → **идентификатор источника**;
- cryptographic identity → **криптографическая идентичность** только если это действительно термин модели безопасности.

Слово **«личность» в инфраструктурном тексте запрещено**.

### Особое правило для `reconcile`

Плохо:

> Flux примиряет манифесты в GKE.

Хорошо:

> Flux применяет изменения и приводит состояние ресурсов GKE к состоянию, описанному в Git.

Или короче:

> Flux синхронизирует состояние кластера с Git-репозиторием.

### Формулировать проверяемое свойство, а не метафору

Плохо:

> Правило узнаёт миграцию по имени.

Хорошо:

> Проверка определяет миграцию по фактически выполняемой команде, а не по имени контейнера.

Плохо:

> Шлюз доказывает, что умеет упасть.

Хорошо:

> На каждом прогоне выполняется отрицательный контроль, подтверждающий, что проверка действительно завершается ошибкой на некорректном входе.

Плохо:

> Зелёный прогон показывает шесть отвергнутых порч.

Хорошо:

> Успешный прогон включает шесть отрицательных тестов и подтверждает, что каждый намеренно повреждённый вход корректно отклоняется.

Плохо:

> Проверка покраснела, когда система заработала.

Хорошо:

> После появления реального состояния проверка стала завершаться ошибкой, потому что тест ошибочно зафиксировал прежнее пустое состояние как инвариант.

### Статусы должны отвечать на четыре вопроса

1. Что произошло?
2. Почему это важно?
3. Что сейчас выполняется?
4. Что требуется дальше?

Не заменять эти ответы метафорами вроде:

- «фронт перезаполнен»;
- «карточка ждёт среду»;
- «кадры W4 ждут вашего слова»;
- «этап стал зелёным».

## 8. Среды и окружения

Использовать точные идентификаторы сред в backticks, а в русском тексте — смысловое название.

| Идентификатор / термин | В тексте |
|---|---|
| dev | среда разработки |
| staging | staging-среда / тестовая среда |
| preprod | предпродуктивная среда |
| prod | продуктивная среда |
| production | продуктивная среда |
| prod-preview | точное имя `prod-preview`; не переводить как «предпросмотр» |
| environment | среда |
| environment projection | конфигурация конкретной среды |
| rendered environment config | итоговая конфигурация среды |

Плохо:

> продвигает в предпросмотр

Хорошо:

> продвигает ту же версию в среду `prod-preview`

## 10. Типичные исправления из инженерного текста

### 10.1 `lane`

Плохо:

> Быстрая полоса пишет дайджесты, глубокая полоса доказывает миграции.

Хорошо:

> Быстрый контур обновляет ссылки на образы в среде разработки. Расширенный контур дополнительно проверяет совместимость миграций и продвигает те же образы в следующую среду.

### 10.2 `identity`

Плохо:

> Сборка выполняется под собственной личностью.

Хорошо:

> Сборка выполняется от отдельной сервисной учётной записи.

### 10.3 `reconcile`

Плохо:

> Flux примиряет манифесты.

Хорошо:

> Flux синхронизирует состояние кластера с манифестами из Git.

### 10.4 `gate`

Плохо:

> Стандартный шлюз не может стать зелёным.

Хорошо:

> Основная проверка готовности релиза пока не проходит.

### 10.5 `trigger`

Плохо:

> Глубокая полоса ещё не проходила целиком от толчка.

Хорошо:

> Расширенный контур ещё не проходил полный сквозной прогон от исходного события запуска.

### 10.6 `ready frontier`

Плохо:

> Фронт перезаполнен двумя задачами.

Хорошо:

> В очередь готовых задач добавлены ещё две задачи.

### 10.7 `sweep`

Плохо:

> Развёртка на 300 сгенерированных входах показала...

Хорошо:

> Массовый прогон на 300 сгенерированных тестовых входах показал...

### 10.8 `residual`

Плохо:

> Проверка приняла работу с остатком.

Хорошо:

> Работа принята с одним незакрытым замечанием.

### 10.9 `healthy signal`

Плохо:

> Это снова здоровый сигнал.

Хорошо:

> Это подтверждает, что основная часть процесса работает корректно.

### 10.10 `green/red`

Плохо:

> Набор тестов должен стать зелёным.

Хорошо:

> Набор тестов должен завершаться успешно.

### 10.11 Kubernetes probe

Плохо:

> Проба готовности стучалась не в ту дверь.

Хорошо:

> Проверка готовности обращалась к неверному endpoint.

### 10.12 Terraform root

Плохо:

> Проверка вычисляется любым планом корня.

Хорошо:

> Проверка выполняется при построении Terraform plan для любого корневого модуля.

## 11. Синтаксис и связность

### Использовать конкретный субъект

Плохо:

> После продвижения откроется второе окно и готовность выйдет на 26/1.

Хорошо:

> После продвижения версии и синхронизации Flux можно выполнить второй этап активации. После него ожидается выполнение 26 из 27 критериев готовности.

Если значение `26/1` не определено, **не угадывать его смысл**. Сохранить исходное обозначение и пояснить только то, что известно.

### Один тезис — одно причинно-следственное отношение

Плохо:

> Третий дефект того же пути, измерен и исправлен — и снова здоровый сигнал: все девять образов собрались...

Хорошо:

> Выявлен и исправлен третий дефект в том же процессе. При этом все девять образов успешно собрались и были опубликованы в реестре, поэтому проблема относится к последующей проверке, а не к этапу сборки.

### Не сжимать текст до потери грамматики

Плохо:

> Проверка чистая: девять образов в реестре, API включён живьём, диф в зоне.

Хорошо:

> Повторная проверка успешна: все девять образов находятся в реестре, API включён в сборочном проекте, а изменения не выходят за рамки требуемой конфигурации.

### Не антропоморфизировать

Плохо:

> Карточка перестала выглядеть готовой к запуску.

Хорошо:

> Задача переведена в состояние `blocked`, поскольку её критерии приёмки пока невозможно проверить в существующих средах.

## 12. Как переводить неоднозначный термин

Перед переводом мысленно выполнить следующие шаги:

1. Определить, является ли слово именем продукта, API, ресурса или внутреннего объекта.
2. Определить техническую роль сущности.
3. Проверить, существует ли устойчивый русский инженерный термин.
4. Если устойчивого термина нет, сохранить английский термин и объяснить его нормальным русским предложением.
5. Не выбирать русский эквивалент только потому, что он является словарным переводом.

Пример для `gate`:

- network gateway → **шлюз**;
- release gate → **проверка готовности релиза**;
- policy gate → **проверка политики**;
- admission gate → **условие допуска / admission-проверка**.

Пример для `identity`:

- human identity → личность / идентичность, в зависимости от смысла;
- IAM identity → субъект IAM / сервисная учётная запись;
- object identity → идентификатор объекта;
- workload identity → Workload Identity.

---

## 13. Правило сохранения точности

Если буквальный русский перевод звучит необычно, это сигнал проверить смысл.

Особенно подозрительны конструкции:

- прилагательное + абстрактное существительное, которых обычно нет в русской инженерной речи;
- неодушевлённый объект «думает», «знает», «ждёт», «видит», «умеет»;
- физическая метафора для программного процесса;
- русский глагол, образованный от английского слова без необходимости;
- слово, которое имеет известное техническое значение в русском, но используется для другого английского понятия.

Примеры подозрительных фраз:

- «сборочная личность»;
- «полоса доставки»;
- «примирить манифесты»;
- «стандартный шлюз» в контексте quality gate;
- «живое доказательство»;
- «здоровый сигнал»;
- «готовый фронт»;
- «перезаполнить фронт»;
- «полный прогон от толчка»;
- «развёртка тестовых входов»;
- «план корня»;
- «проверка читает написание»;
- «проверка стала зелёной»;
- «остаток записан открыто».

При появлении такой фразы **переформулировать предложение целиком**, а не заменять одно слово.

## 14. Стиль инженерного статуса

Предпочтительный шаблон:

> **Состояние.** Что сейчас работает или не работает.  
> **Причина.** Какая конкретная техническая причина установлена.  
> **Подтверждение.** Каким тестом, логом, конфигурацией или реальным прогоном это подтверждено.  
> **Следующий шаг.** Какое конкретное действие осталось выполнить.

Пример:

> Релизная сборка успешно создаёт и публикует все девять образов. Последующий этап проверки происхождения образов завершался ошибкой, потому что в сборочном проекте не был включён Container Analysis API. API добавлен в Terraform-конфигурацию и включён; контрольная сборка от той же сервисной учётной записи завершилась успешно. Следующий шаг — повторить полный релизный прогон.

---

## 15. Стиль анализа дефекта

Предпочтительный шаблон:

> **Дефект:** что именно было неверно.  
> **Почему не обнаружили раньше:** какой слой проверки отсутствовал.  
> **Как воспроизвести:** минимальный способ получить ошибку.  
> **Как предотвратить:** автоматическая проверка, которая должна ловить класс ошибок до облачного/E2E-прогона.

Плохо:

> Доказательство доказывает не то.

Хорошо:

> Проверка не подтверждает заявленное свойство: успешный результат возможен даже в состоянии, в котором проверяемое действие вообще не выполняется. Нужен положительный контроль, подтверждающий, что тест действительно наблюдает требуемое действие.

## 16. Формальный словарь предпочтений

Следующие замены считать нормативными по умолчанию:

- **полоса** → контур / ветвь пайплайна;
- **личность** → сервисная учётная запись / субъект IAM / идентификатор;
- **примирять** → синхронизировать / приводить к требуемому состоянию;
- **шлюз** для `gate` → проверка / контрольный этап;
- **толчок** → событие запуска / триггер;
- **фронт** → очередь готовых задач;
- **остаток** → оставшийся пункт / замечание / проблема;
- **живой прогон** → реальный прогон;
- **живое доказательство** → подтверждение в реальной среде;
- **здоровый сигнал** → положительный признак / подтверждение корректности;
- **покраснеть** → завершиться ошибкой;
- **позеленеть** → завершиться успешно;
- **развёртка входов** → массовый прогон / серия тестов;
- **обзор** для `review` → ревью / проверка;
- **круг** для iteration → итерация;
- **ограждение** для `guardrail` → защитное ограничение;
- **преграда** для validation barrier → независимая проверка;
- **путь доставки** → процесс / контур доставки;
- **план корня** → Terraform plan корневого модуля;
- **форма конфигурации** → вариант / структура конфигурации;
- **подаёт сборку** → запускает / отправляет сборку на выполнение;
- **отрендерить** → сформировать / сгенерировать;
- **резолвится** → определяется / разрешается / соответствует;
- **деплоит** → развёртывает;
- **триггерится** → запускается;
- **стучится в дверь** → обращается к endpoint/порту;
- **диф в зоне** → изменения не выходят за рамки задачи;
- **собственная личность** → отдельная сервисная учётная запись;
- **предпросмотр** для environment `prod-preview` → среда `prod-preview`;
- **карточка ждёт** → выполнение задачи зависит от;
- **кадры W4** → задачи/элементы `W4`, если точный смысл `frame` не определён.

## 17. Финальная самопроверка перед ответом

Перед отправкой русского технического текста проверить:

- Есть ли «полоса» в значении `lane`?
- Есть ли «личность» в IAM/GCP/Kubernetes-контексте?
- Есть ли «примирять» в GitOps-контексте?
- Переведён ли `gate` как «шлюз»?
- Есть ли «толчок» в значении `trigger`?
- Есть ли «фронт» в значении очереди задач?
- Есть ли «здоровый», «живой», «красный», «зелёный» как машинные метафоры?
- Есть ли «остаток» без точного существительного: проблема, замечание, задача?
- Есть ли англицизированный русский глагол, который можно заменить нормальным техническим глаголом?
- Есть ли фраза, грамматика которой повторяет английский порядок слов?
- Понятно ли, какой конкретный компонент выполняет действие?
- Не потерялось ли точное имя ресурса из-за перевода?
- Можно ли прочитать абзац без знания исходной английской фразы?

Если хотя бы один ответ вызывает сомнение — переписать предложение по смыслу целиком.

## 18. Краткая директива для модели

**Пиши на грамотном современном русском языке в стиле инженерной документации. Не делай дословный перевод англоязычной технической речи. Сохраняй точные имена продуктов, API, ресурсов и идентификаторов, но описывай их действия естественными русскими конструкциями. Предпочитай конкретные термины и причинно-следственные формулировки метафорам.
